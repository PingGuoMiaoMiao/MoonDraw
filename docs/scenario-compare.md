# 同一编辑场景下的能力对比

本文件回答初审意见的第 ④ 点：「请补充同一编辑场景下的能力对比」。

不使用「谁有哪个功能」的矩阵——那种对比无法说明编辑机制。这里用**同一任务、两条工作流**，
把每一步的代价摆出来。MoonDraw 一侧的数字均为本仓库命令行实测，可复现；Moonlight 一侧
依据其仓库 HEAD（`62276b9`）的数据模型推断其可行操作，不做能力臆测。

对比对象：`mizchi/moonlight`（MoonBit 写的 SVG 白板编辑器，like Excalidraw）。

---

## 场景 A：在流程中间插入一个审批环节

**任务**：已有 `提交 → 审批 → 发布`，要求在「审批」与「发布」之间插入「法务复核」。

### Moonlight 一侧

其元素模型是 `Element { x, y, shape: ShapeType, style, parent_id, connections }`，
`ShapeType` 为几何图元（Rect/Circle/Ellipse/Line/Polyline/Path），坐标即用户摆放的位置，
布局阶段不存在。

| 步骤 | 操作 |
|---|---|
| 1 | 在空白处画出新的矩形 |
| 2 | 手动把「发布」及其下方相关元素向下拖出空间 |
| 3 | 移动或重画两条连线，使其分别连到新节点上下 |
| 4 | 手工对齐，使三个节点纵向居中对齐 |
| 5 | 若下方还有节点，重复步骤 2–4 |

**可复现性**：结果取决于拖拽精度，换人做会得到不同坐标。

### MoonDraw 一侧

```bash
# 改一行文本
$ cat after.mmd
flowchart TD
  A[提交] --> B[审批]
  B --> N[法务复核]
  N --> C[发布]

# 重新导出
$ moondraw render after.mmd out.svg
已写入 out.svg · 节点 4 · 边 3 · 无环
```

| 步骤 | 操作 |
|---|---|
| 1 | 文本中插入一行 |

**实测坐标**（`moondraw layout`）：

| 节点 | 插入前 | 插入后 |
|---|---|---|
| 提交 | (12, 12) | (12, 12) |
| 审批 | (12, 96) | (12, 96) |
| 法务复核 | — | (12, 180) |
| 发布 | (12, 180) | (12, 264) |

**可复现性**：同输入必得同输出；「发布」被自动推到 y=264，无需人工挪动。

### 差异要点

不是「多一个自动布局按钮」，而是**坐标的所有权归属不同**：Moonlight 的坐标是编辑对象，
MoonDraw 的坐标是计算产物。所以在 MoonDraw 里，插入节点不需要处理任何空间关系。

## 场景 B：把图从纵向改成横向

**任务**：同一张 7 节点审批流程图，从「自上而下」改为「从左到右」。

### Moonlight 一侧

坐标是用户摆放的，方向不是属性。要改变排布方向，只能重新摆放所有元素。

### MoonDraw 一侧

```bash
$ moondraw layout ticket.mmd --direction DOWN | head -3
  收到工单  @(65,12)
  是否 P1   @(45,96)
  立即响应  @(222,228)

$ moondraw layout ticket.mmd --direction RIGHT | head -3
  收到工单  @(12,44)
  是否 P1   @(152,28)
  立即响应  @(352,138)
```

一次参数变更，全部坐标重算；文本图本身没有改动。

### 差异要点

方向是**布局属性**而非编辑结果。同一个图可以有多套合法排布，切换不损失任何信息。

## 场景 C：换一种布局风格

**任务**：同一张图，分别用分层、力导向、矩形装箱三种方式排布，挑一个最合适的。

### MoonDraw 一侧（实测同一张 `ticket.mmd`）

| 算法 | 收到工单 | 是否 P1 | 立即响应 |
|---|---|---|---|
| layered | (65, 12) | (45, 96) | (222, 228) |
| force | (56, 411) | (92, 50) | — |
| rectpacking | (15, 15) | (150, 15) | — |

三种结果差异显著：分层强调层级，力导向按连接张力散开，装箱按矩形紧凑排列。

```bash
$ moondraw render ticket.mmd a.svg --algorithm layered
$ moondraw render ticket.mmd b.svg --algorithm force
$ moondraw render ticket.mmd c.svg --algorithm rectpacking
```

### Moonlight 一侧

无布局算法可选——没有布局阶段，也就没有「风格」这个维度。

## 场景 D：图的结构是否合法

**任务**：在发布前确认这张图没有形成循环依赖。

```bash
$ moondraw check cycle.mmd
节点 3 · 边 3 · ⚠ 存在环

$ moondraw check ticket.mmd
节点 7 · 边 7 · 无环
```

这条检查需要遍历边集做 DFS。Moonlight 的连线是携带锚点的 `Line` 元素，
没有「边连通哪两个节点」这一层抽象，因此无法回答「图里有没有环」。

## 汇总

| 维度 | Moonlight | MoonDraw |
|---|---|---|
| 坐标来源 | 用户拖拽 | 布局算法派生 |
| 插入节点 | 挪动 + 重连 + 对齐 | 改一行文本 |
| 改变方向 | 重新摆放 | 一个参数 |
| 布局风格 | 无此概念 | 6 种可选算法 |
| 结构校验 | 无法表达 | `check` 做环检测/孤立节点/悬空边 |
| 无浏览器运行 | 不支持（依赖 luna/js_browser） | `cli.exe` native 3.4 MB |
| 结果可复现 | 依赖人工精度 | 同输入同输出 |

## 边界说明（不主张的部分）

- Moonlight 的**手绘与贝塞尔拟合**、**暗色主题**、**Embed / Web Component 多入口**、
  **486 个测试**均强于本项目，本项目不提供等效能力。
- 本项目的编辑器前端（在线版）在交互手感上不优于 Moonlight，它的存在只是证明内核
  能在真实交互下工作，不是本项目的主张。
- 本项目不主张「用 MoonBit 写」本身构成差异——双方都用 MoonBit。
